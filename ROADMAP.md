## 1. Как пользоваться этим планом

Не пытайся делать всё сразу. Работай **строго по этапам**:

1. Сначала определи доменную модель и БД.
2. Потом сделай DTO и валидацию.
3. Потом репозитории.
4. Потом сервисы.
5. Потом security.
6. Потом контроллеры.
7. Потом обработку ошибок.
8. Потом OpenAPI и README.
9. Потом тесты.
10. Потом Docker и полировка.

### Главный принцип
Каждый этап считается завершённым только тогда, когда:
- код компилируется;
- логика проходит ручную проверку;
- есть понятный результат в API или БД;
- следующий этап может опираться на предыдущий без костылей.

### Как лучше работать
- Делай **один смысловой блок за раз**.
- После каждого блока запускай сборку и тесты.
- Не переходи к security, пока не готова бизнес-модель.
- Не начинай писать контроллеры, пока не понятны сервисы и DTO.
- Не добавляй Swagger до того, как стабилизируются эндпоинты.

## 2. Цель проекта

Сделать backend-систему управления банковскими картами, где:

- пользователь может видеть только свои карты;
- администратор может управлять всеми картами;
- карта хранится безопасно;
- переводы происходят между картами одного владельца;
- операции защищены JWT;
- вся бизнес-логика отделена от контроллеров;
- схема БД создаётся миграциями;
- API документируется и тестируется.

---

## 3. Идеальная архитектура проекта

Проект лучше строить по слоям:

- `entity` — сущности БД;
- `dto` — входные и выходные модели API;
- `repository` — работа с БД;
- `service` — бизнес-логика;
- `controller` — HTTP-слой;
- `security` — JWT и доступы;
- `exception` — ошибки и единый формат ответа;
- `mapper` — преобразование сущностей в DTO и обратно;
- `util` — вспомогательные функции;
- `config` — конфигурация;
- `docs` — OpenAPI и документация;
- `src/test` — тесты.

### Почему так
Это помогает:
- не смешивать HTTP и бизнес-логику;
- не возвращать entity наружу;
- не дублировать код;
- проще тестировать;
- проще менять реализацию без ломки API.

## 5. Этап 1. Зафиксировать доменную модель

Это самый важный этап. Если здесь ошибиться, потом придётся переделывать почти всё.

### 5.1. Определить сущность `User`

#### Что должно быть у пользователя
- `id`
- `username`
- `email`
- `password`
- `role`
- `createdAt`
- связь с картами

#### Зачем
Пользователь нужен для:
- авторизации;
- проверки прав доступа;
- привязки карт к владельцу.

#### Что сделать
1. Определить типы полей.
2. Добавить уникальные ограничения на `username` и `email`.
3. Продумать связь `OneToMany` с картами.
4. Решить, кто создаёт пользователей: админ, регистрация или seed-данные.

#### Как проверять
- Можно ли однозначно найти пользователя по `username`.
- Можно ли связать пользователя с несколькими картами.
- Хранится ли пароль только как хэш.

---

### 5.2. Определить сущность карты

#### Какие поля нужны
- `id`
- `cardNumberEncrypted`
- `cardNumberMasked`
- `owner`
- `cardholderName`
- `expiresAt`
- `status`
- `balance`
- `createdAt`

#### Почему именно так
- Номер карты нельзя хранить в открытом виде.
- Пользователю нельзя показывать полный номер карты.
- Баланс должен быть отдельным числовым полем.
- Статус нужен для блокировки и истечения срока.

#### Что сделать
1. Определить enum статусов: `ACTIVE`, `BLOCKED`, `EXPIRED`.
2. Определить тип денег: обычно `BigDecimal`.
3. Описать связь с владельцем карты.
4. Продумать правила обновления статуса по сроку действия.

#### Как проверять
- Можно ли получить только маску карты.
- Можно ли отфильтровать карты по статусу.
- Можно ли безопасно переводить деньги только между допустимыми картами.

---

### 5.3. Решить вопрос с названием сущности карты

#### Варианты
- оставить `CardImpl`;
- переименовать в `Card`.

#### Рекомендация
Если проект твой и ты делаешь его для портфолио — лучше использовать **понятное доменное имя**, то есть `Card`.

#### Зачем
- `CardImpl` выглядит как техническая реализация, а не сущность.
- Проще читать код.
- Проще писать сервисы и тесты.

#### Что сделать
- выбрать один вариант и придерживаться его везде;
- не смешивать `Card` и `CardImpl` в одном API.

## 6. Этап 2. Спроектировать базу данных и Liquibase

Сначала проектируется БД, потом всё остальное.

### 6.1. Таблицы

Обычно нужны:
- `users`
- `cards`

Возможно позже:
- таблица операций;
- таблица refresh-token;
- таблица аудита.

### 6.2. Что должно быть в `users`
- идентификатор;
- уникальный логин;
- email;
- пароль;
- роль;
- дата создания.

### 6.3. Что должно быть в `cards`
- идентификатор;
- владелец (`owner_id`);
- зашифрованный номер;
- маска;
- имя держателя;
- срок действия;
- статус;
- баланс;
- дата создания.

### 6.4. Что сделать в Liquibase
1. Проверить `db.changelog-master.yaml`.
2. Разбить схему на отдельные changelog-файлы.
3. Добавить создание таблиц.
4. Добавить foreign key.
5. Добавить уникальные индексы.
6. Добавить индексы по часто ищущимся полям.
7. Добавить начального admin-пользователя.

### 6.5. Зачем это нужно
Liquibase делает схему БД:
- повторяемой;
- воспроизводимой;
- безопасной для команды;
- удобной для развёртывания.

### 6.6. Как проверять
- База создаётся с нуля без ручного вмешательства.
- Таблицы и связи соответствуют сущностям.
- Повторный запуск миграций не ломает базу.

### 6.7. Типичные ошибки
- забыть foreign key;
- хранить пароль не в хэше;
- сделать nullable-поле там, где оно обязательно;
- не индексировать `username` и `email`;
- хранить карту в открытом виде.

## 7. Этап 3. DTO и валидация

DTO нужны, чтобы отделить API от внутренней модели.

### 7.1. Входные DTO

Нужны модели для:
- создания карты;
- перевода между картами;
- логина;
- возможно, создания пользователя.

### 7.2. Выходные DTO

Нужны модели для:
- ответа по карте;
- ответа по переводу;
- ответа по авторизации;
- ответа по пользователю, если он нужен.

### 7.3. Что должно быть в DTO
Только то, что реально нужно клиенту.

#### Пример логики
- клиент передаёт параметры для создания карты;
- сервер генерирует секретные данные сам;
- клиент не должен передавать зашифрованный номер карты;
- клиент не должен видеть raw password.

### 7.4. Зачем это нужно
DTO позволяют:
- скрыть внутреннюю структуру сущностей;
- делать понятный контракт API;
- добавлять валидацию;
- не ломать БД при изменении API.

### 7.5. Валидация
Добавляй проверки:
- `@NotBlank`
- `@NotNull`
- `@Email`
- `@Positive`
- `@DecimalMin`
- ограничения длины строк.

### 7.6. Как проверять
- Нельзя отправить пустой логин.
- Нельзя отправить отрицательную сумму.
- Нельзя создать карту без владельца.
- Нельзя передать некорректную дату.

## 8. Этап 4. Репозитории

Репозиторий отвечает только за работу с БД.

### 8.1. Что нужно сделать
1. Сделать репозиторий пользователей.
2. Сделать репозиторий карт.
3. Добавить методы поиска под нужные сценарии.

### 8.2. Какие методы обычно нужны
Для пользователя:
- поиск по `username`;
- поиск по `email`;
- проверка существования логина.

Для карты:
- поиск по владельцу;
- поиск по статусу;
- поиск по `id`;
- возможно, поиск по маске или последним цифрам.

### 8.3. Зачем
Чтобы сервисы не писали SQL руками и не хранили логику доступа к БД внутри контроллеров.

### 8.4. Что проверить
- Репозиторий возвращает корректные сущности.
- Методы поиска не дублируют друг друга.
- Нет лишних manual implementation, если Spring Data уже умеет это сам.

### 8.5. Важное замечание
Если у тебя есть классы вроде `UserRepositoryImpl` и `CardRepositoryImpl`, сначала проверь, действительно ли они нужны.

Чаще всего в Spring Data достаточно:
- интерфейса репозитория;
- наследования от `JpaRepository`;
- дополнительных query-методов.

## 9. Этап 5. Сервисный слой

Это сердце проекта. В сервисах живёт бизнес-логика.

### 9.1. Общий принцип
Контроллер принимает запрос, сервис решает, что делать, репозиторий работает с БД.

### 9.2. Какие сервисы нужны
Обычно нужны:
- сервис аутентификации;
- сервис карт;
- возможно, сервис пользователей;
- возможно, сервис операций.

### 9.3. Что должен делать сервис карт

#### Сценарии пользователя
- получить список своих карт;
- посмотреть баланс;
- перевести деньги между своими картами;
- запросить блокировку своей карты;
- фильтровать и постранично получать список.

#### Сценарии администратора
- создать карту;
- получить все карты;
- заблокировать карту;
- активировать карту;
- удалить карту.

### 9.4. Что важно в логике переводов
1. Проверить владельца обеих карт.
2. Проверить статус карт.
3. Проверить, хватает ли денег.
4. Провести операцию транзакционно.
5. Списать деньги с одной карты и зачислить на другую.
6. Сохранить изменения атомарно.

### 9.5. Что важно в логике создания карты
- номер карты генерируется на сервере;
- клиент не передаёт его напрямую;
- номер хранится в зашифрованном виде;
- наружу отдаётся маска.

### 9.6. Почему сервер генерирует номер карты
Потому что:
- клиент может подделать данные;
- номер карты должен быть контролируемым и уникальным;
- сервер может сразу применить шифрование и маскирование;
- это уменьшает риск компрометации.

### 9.7. Как проверять сервисы
- Сервис возвращает корректный результат.
- При ошибке кидает понятное исключение.
- Перевод без денег невозможен.
- Перевод между чужими картами невозможен.
- Заблокированную карту нельзя использовать в переводе.

### 9.8. Важная техническая деталь
Не используй `java.awt.print.Pageable`.
Нужен `org.springframework.data.domain.Pageable`.

Это частая ошибка, которая ломает пагинацию.

## 10. Этап 6. Security: JWT и роли

Без этого проект не будет настоящим банковским backend'ом.

### 10.1. Что должно быть реализовано
- логин по username/password;
- генерация JWT;
- проверка JWT в фильтре;
- роли `ADMIN` и `USER`;
- доступ к endpoint'ам по ролям;
- доступ к собственным данным только владельцу.

### 10.2. Какие компоненты нужны
Обычно нужны:
- `UserDetailsService`;
- JWT util;
- JWT filter;
- `SecurityConfig`;
- `PasswordEncoder`;
- возможно, `AuthenticationManager`.

### 10.3. Зачем нужен JWT
JWT нужен, чтобы:
- не хранить сессию на сервере;
- проверять пользователя на каждом запросе;
- передавать роль и идентификатор пользователя в токене;
- защитить API.

### 10.4. Как должен работать поток
1. Пользователь отправляет логин и пароль.
2. Сервер проверяет пароль.
3. Сервер выдаёт JWT.
4. Клиент отправляет JWT в `Authorization: Bearer ...`.
5. Фильтр проверяет токен.
6. Spring Security пускает или не пускает к endpoint.

### 10.5. Что проверять
- Без токена нельзя попасть в защищённый API.
- С неправильным токеном запрос отклоняется.
- `USER` не может вызвать `ADMIN`-endpoint.
- Пароль хранится только как BCrypt hash.

### 10.6. Где часто ошибаются
- забывают подключить фильтр в security chain;
- делают слишком слабый secret key;
- не закрывают публичные endpoint'ы;
- не проверяют роль на уровне метода или URL;
- возвращают подробности о внутренней ошибке авторизации.

## 11. Этап 7. Контроллеры

Контроллер — это только HTTP-слой.

### 11.1. Что он делает
- принимает запрос;
- валидирует вход;
- вызывает сервис;
- возвращает DTO;
- не содержит бизнес-логики.

### 11.2. Какие контроллеры лучше иметь
- `AuthController` — логин;
- `CardController` — пользовательские операции;
- `AdminCardController` — админские операции;
- при необходимости `UserController`.

### 11.3. Как строить endpoint'ы
Хорошая логика:
- `/api/auth/login`
- `/api/cards`
- `/api/cards/{id}/balance`
- `/api/cards/{id}/block`
- `/api/cards/transfer`
- `/api/admin/cards`
- `/api/admin/cards/{id}/block`
- `/api/admin/cards/{id}/activate`
- `/api/admin/cards/{id}`

### 11.4. Что важно в контроллерах
- не принимать entity как вход;
- не возвращать entity как ответ;
- не хранить в них сложную логику;
- не дублировать проверки, которые должны быть в сервисе.

### 11.5. Как проверять
- Endpoint принимает правильный JSON.
- Возвращает DTO, а не сущность.
- Пагинация и фильтрация работают через query params.
- Неправильный вход даёт понятную ошибку.

## 12. Этап 8. Исключения и единый формат ошибок

Без нормального error handling API выглядит сырым.

### 12.1. Что нужно сделать
- создать доменные исключения;
- добавить `@RestControllerAdvice`;
- вернуть единый формат ошибок.

### 12.2. Типы исключений
Обычно нужны:
- `NotFoundException`;
- `AccessDeniedException`;
- `InsufficientFundsException`;
- `InvalidCardStatusException`;
- `DuplicateResourceException`;
- `ValidationException`.

### 12.3. Зачем
Чтобы клиент получал:
- понятный статус;
- понятное сообщение;
- одинаковую структуру ответа.

### 12.4. Что должно быть в ответе ошибки
Рекомендуемый формат:
- timestamp;
- status;
- error;
- message;
- path;
- details при ошибке валидации.

### 12.5. Что проверять
- Ошибка карты возвращает 404.
- Недостаточно средств — 400 или 409 по принятой политике.
- Валидация — 400.
- Нет доступа — 403.
- Неавторизован — 401.

## 15. Этап 11. Тестирование

Тесты нужно писать после того, как логика уже более-менее стабилизировалась.

### 15.1. Какие тесты нужны

#### Unit-тесты сервисов
Проверяют бизнес-логику без поднятия всего приложения.

#### Controller-тесты
Проверяют HTTP-контракт и статус-коды.

#### Security-тесты
Проверяют доступы, роли и авторизацию.

#### Repository-тесты
Проверяют работу с БД.

### 15.2. Что обязательно тестировать
- успешную авторизацию;
- отказ при неверном пароле;
- создание карты;
- просмотр только своих карт;
- блокировку карты;
- перевод между своими картами;
- отказ при недостатке средств;
- отказ при доступе к чужой карте;
- админский доступ;
- валидацию входных данных.

### 15.3. Зачем тесты нужны именно здесь
Потому что у проекта много критичных правил:
- деньги;
- доступ;
- роли;
- статусы карты;
- безопасность.

### 15.4. Как проверять тестами
- Сервис не допускает недопустимые операции.
- Контроллер возвращает правильный статус.
- Security режет чужой доступ.
- Репозиторий корректно ищет данные.

## 20. Типичные ошибки, которых лучше избежать

- Смешивание entity и DTO.
- Логика в контроллере.
- Ручной SQL там, где достаточно репозитория.
- Использование неправильного `Pageable`.
- Хранение номера карты в открытом виде.
- Возврат полного номера карты наружу.
- Отсутствие транзакции при переводе денег.
- Отсутствие проверки прав доступа.
- Отсутствие централизованной обработки ошибок.
- Отсутствие тестов для критичных сценариев.
